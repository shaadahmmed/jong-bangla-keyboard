# First-release requirements and development steps

## Confirmed requirements

| Area | Decision |
| --- | --- |
| Working project name | `jong-bangla-board` |
| Display name | Proposed: Jong Bangla |
| License | MIT |
| Implementation | From scratch, with Rust engine and composition logic |
| First integration | Fcitx5 on Linux |
| Display session | Wayland first |
| First test environment | CachyOS + KDE Plasma; versions to record during setup |
| Phonetic behavior | Target jsAvroPhonetic v1.1.4 conversion behavior; exact revision below |
| Composition | Keep the current word editable until a boundary commits it |
| Backspace | Remove the last raw phonetic keystroke and recompute Bangla |
| Choices | Converted Bangla first; exact original Latin input second |
| Numbers | Bangla digits by default |
| Autocorrection | Separate, extensible functionality; no correction rules enabled initially |
| Performance | Fast, lightweight, offline; measurable budgets still to establish |
| Later platforms | IBus and Windows, reusing the Rust engine |

The two choices are deterministic representations of the same input, not
dictionary suggestions. The Latin choice preserves the original input, including
case and digits. It does not translate the Bangla word into English.

## Composition model

The engine stores the raw keystrokes for the active word. It derives the Bangla
output from that buffer and exposes both outputs to the platform adapter.

**Preedit** is the current, uncommitted text shown in the application. **Commit**
means inserting the selected output into the application's document. Before
commit, Backspace edits the raw input and recomputes the whole active word. After
commit, ordinary document editing belongs to the application; v1 does not promise
to recover raw keystrokes from already committed Bangla.

Spaces, punctuation, and Enter are intended word boundaries. Exact punctuation
handling must respect phonetic sequences that use punctuation or escape keys:
do not commit every punctuation key unconditionally before matching the rules.

## Proposed interaction details

These defaults need to be settled before the composition controller is built.
They are not yet confirmed requirements.

| Event | Proposed behavior |
| --- | --- |
| New composition | Select the Bangla choice by default |
| Up/Down while choices are visible | Change the selected choice |
| Space with active composition | Commit the selected choice and insert a space |
| Enter with active composition | Commit the choice and consume Enter; a subsequent Enter reaches the app |
| Escape with active composition | Cancel the active composition |
| Backspace with an empty buffer | Let the application handle it |
| Digits | Enter digits, converting them to Bangla in the Bangla choice; no numeric selection shortcuts |
| Language switching | Use Fcitx5's configured switching controls; no separate global shortcut initially |
| Other application shortcuts | Preserve normal application behavior; finalize modifier handling in adapter work |

Focus loss, input-method switching, cursor/navigation keys, mouse movement,
selection changes, and sensitive input contexts need explicit commit/reset
policies and integration tests before the first usable release. Avoid retaining
one application's composition when typing into another.

## Proposed architecture

1. **Transliteration core (Rust):** deterministic raw-input-to-Bangla conversion;
   no knowledge of Fcitx5, Wayland, dictionaries, or desktop UI.
2. **Composition controller (Rust):** raw buffer, two choices, selected choice,
   editing, and explicit commit/cancel/reset actions.
3. **Fcitx5 adapter:** translates framework events into controller actions and
   sends preedit, candidates, and committed text back to Fcitx5.

Autocorrection should be a separate optional stage that can be added without
changing the deterministic core. The first implementation need not include a
plugin loader, a dictionary, or a no-op extension framework.

The official [Fcitx5 addon tutorial](https://fcitx-im.org/wiki/Develop_an_simple_input_method)
documents C++ shared-library addons and CMake. Investigate the smallest practical
Rust interoperability approach with a minimal addon experiment. A thin C++ bridge
is a candidate; do not promise an entirely Rust addon before validating the API.
Record the chosen boundary and build instructions when that experiment succeeds.

The official [Fcitx5 Wayland guide](https://fcitx-im.org/wiki/Using_Fcitx_5_on_Wayland/en)
describes compositor- and application-dependent integration. Test on CachyOS +
KDE Plasma first and record versions. An XWayland application test is useful but
does not establish native Wayland support. Broader support requires more testing.

## Phonetic behavior reference

Selected on 2026-10-28: **jsAvroPhonetic v1.1.4**, from
[torifat/jsAvroPhonetic](https://github.com/torifat/jsAvroPhonetic), pinned to
commit [`d3790172ebff92d43f0294bc51fed1fca7c80039`](https://github.com/torifat/jsAvroPhonetic/tree/d3790172ebff92d43f0294bc51fed1fca7c80039).

[OmicronLab's developer resources](https://www.omicronlab.com/developers.html)
identify this project as its official JavaScript implementation. It offers a
conversion reference that can be exercised independently of a desktop input
method. `git ls-remote` confirmed v1.1.4 as the newest published tag on the
selection date; the pinned `bower.json` also reports 1.1.4. The repository's
current default branch is a different revision. Pinning the tagged revision
keeps future comparisons repeatable rather than following a moving branch.

The scope is deterministic phonetic conversion to Unicode Bangla. Dictionary
suggestions, autocorrection, candidate ranking, and browser UI behavior are
outside this comparison. Composition controls remain this project's separate
decisions. This reference selection does not establish parity with all Avro
implementations or current Avro Keyboard for Windows.

The [README at the pinned revision](https://github.com/torifat/jsAvroPhonetic/blob/d3790172ebff92d43f0294bc51fed1fca7c80039/README.md)
declares MPL-1.1. It is a behavior reference, not a dependency or a source of
copied code: no upstream engine, rule tables, or fixtures have been imported into
the project.
Our implementation and initial examples are independently authored under
the project's MIT license. Any later import requires its own provenance and
license review.

All 225 authored cases (27 initial, 66 `a`/`i`, 80 `u`/`U`, and 52 `I`) have been
compared against this exact revision's `OmicronLab.Avro.Phonetic.parse(input)` entry point.
The invocation is documented in the
[README](../README.md#repeat-the-reference-comparison), inputs
and code points in the [initial](../tests/fixtures/reference.tsv),
[`a`/`i`](../tests/fixtures/vowels.tsv), [`u`/`U`](../tests/fixtures/vowels-u.tsv), and
[`I` fixtures](../tests/fixtures/vowels-i-long.tsv), and actual checks
in the [progress log](progress.md). Passing this set establishes only these cases.

## First conversion slice

Implemented on 2026-10-28 as a single Rust library package, `jong-bangla-core`.
`transliterate(&str) -> String` performs conversion without platform APIs, mutable
composition state, external dependencies, or input persistence. Rust 2024 edition
and Rust/Cargo 1.99.1 are the initial development baseline, matching the validated
current stable toolchain. Older toolchains have not been tested.

The initial sequence set is deliberately small; the vowel groups below extend
this baseline:

| Raw input | Output | Unicode |
| --- | --- | --- |
| `k`, `kh` | ক, খ | U+0995, U+0996 |
| `g`, `gh` | গ, ঘ | U+0997, U+0998 |
| `t`, `th` | ত, থ | U+09A4, U+09A5 |
| `T`, `Th` | ট, ঠ | U+099F, U+09A0 |
| `n`, `N` | ন, ণ | U+09A8, U+09A3 |
| `b`, `bh` | ব, ভ | U+09AC, U+09AD |
| `m` | ম | U+09AE |
| `0`–`9` | ০–৯ | U+09E6–U+09EF |

In the initial slice, the longest supported consonant sequence was selected at
each input position, with exact case matching. Otherwise one complete Unicode
character was copied unchanged. The vowel groups add context below.
Unsupported sequences can contain supported parts, so preservation applies to
unmatched characters, not necessarily an entire word. No Unicode normalization
is performed. Existing Bangla, non-ASCII digits, and other unmatched Unicode
characters are preserved. This slice does not provide composition controls or
the literal Latin candidate; those require the later controller.

Reference-checked cases cover the 13 consonant sequences individually, all ten
digits individually and together, `kh12T`, `t T th Th n N`, and `[2026]`.
The fixtures were authored for this project; no upstream tests or rule tables
were imported. The external reference parser was downloaded only to a temporary
directory and evaluated for comparison with Node.js v24.21.0. Its SHA-256 is
`312ed3438ebf0a69f6de38036572ec39cdbafe3ef53f500caa402aaa704c2b32`.

Initial gaps observed with the same reference parser (`a` and `ka` are now
resolved by the first vowel group below):

| Input | Initial slice | Reference | Missing behavior |
| --- | --- | --- | --- |
| `a` | a | আ (U+0986) | Independent vowels |
| `ka` | কa | কা (U+0995 U+09BE) | Contextual vowel signs |
| `kkh` | কখ | ক্ষ (U+0995 U+09CD U+09B7) | Conjunct sequences |
| `K` | K | ক (U+0995) | Case normalization for some letters |
| `` k`h `` | ক`h | কহ (U+0995 U+09B9) | Escape handling and unsupported `h` |

These are temporary coverage limits, not intended v1 behavior. Punctuation and
backticks are currently literal; they do not commit text or apply phonetic
rules. Arbitrary concatenations of supported consonants are not a compatibility
claim because longer or contextual rules are still absent. Backspace, selection,
commit, cancel, focus handling, and platform testing remain later work.

## First vowel group

Added on 2026-10-28: lowercase `a` and `i`, with context tracked locally during
each conversion call. This is transliteration context, not editable composition
state, and nothing is retained between calls.

| Context | `a` | `i` |
| --- | --- | --- |
| Start, or after a digit/unmatched character | আ (U+0986) | ই (U+0987) |
| Immediately after a supported consonant token | া (U+09BE) | ি (U+09BF) |
| Immediately after lowercase `i` | য়া (U+09DF U+09BE) | ই (U+0987) |
| Immediately after lowercase `a` | আ (U+0986) | ই (U+0987) |

For example, `ka` now produces `কা`, `ki` produces `কি`, `ami` produces `আমি`,
and `kia` produces `কিয়া`. The vowel sign for `i` is encoded after its consonant
(U+0995 U+09BF in `কি`), even though a font displays the sign to its left. The
`য়` in the `ia` sequence is U+09DF, matching the reference exactly; the engine
does not normalize or substitute a visually similar Unicode sequence.

Only recognized consonant tokens establish consonant context. Existing Bangla,
emoji, punctuation, whitespace, combining marks, digits, and unsupported Latin
letters end that context. Thus `কi` produces `কই`, and `k1a` produces `ক১আ`.
This prevents vowel signs from attaching to copied Unicode text. Vowel context
also ends at such characters: `i a` produces `ই আ`, without an inserted `য়`.

The 66 independently authored [vowel cases](../tests/fixtures/vowels.tsv) cover
each supported consonant with both vowels, repeated and adjacent vowels, digits,
word separators, mixed Unicode, and several words. Their expected output and
code points were checked against the pinned parser before the Rust rules were
implemented. Together with the original 27 cases, all 93 match. The Rust tests
also check control-character boundaries, combining marks, and separate calls.

That increment left uppercase `A`/`I`, other vowels, and context after unsupported
Latin consonants unimplemented. The next group below adds `u`/`U`.
For example, `qa` produces
`qআ` while the reference produces `কা`; this engine does not yet recognize `q`.
Backtick escapes still pass through literally: `` i` `` produces `ই` followed
by a backtick, while the reference produces U+09BF alone. No broader compatibility,
composition, or platform support is established by this increment.

## Second vowel group

Added on 2026-10-28: case-sensitive `u` and `U`, extending the same conversion-local
context used by `a`/`i`.

| Context | `u` | `U` |
| --- | --- | --- |
| Start, or after a digit/unmatched character | উ (U+0989) | ঊ (U+098A) |
| Immediately after a supported consonant token | ু (U+09C1) | ূ (U+09C2) |
| Immediately after any supported vowel | উ (U+0989) | ঊ (U+098A) |

An `a` immediately after `u` or `U` produces য়া (U+09DF U+09BE), as it already
does after `i`. Thus `kua` → `কুয়া` and `kUa` → `কূয়া`. An `i` after either form
remains independent: `kui` → `কুই`, `kUi` → `কূই`. Repeated vowels are separate:
`uu` → `উউ`, `uU` → `উঊ`, `Uu` → `ঊউ`, `UU` → `ঊঊ`.

Case remains meaningful: `bhumi` → `ভুমি`, `bhUmi` → `ভূমি`. Both results follow
the typed sequence without a dictionary or spelling correction. Other examples
include `tumi` → `তুমি` and `khuki` → `খুকি`.

The 80 new [fixtures](../tests/fixtures/vowels-u.tsv) were independently authored
and reference-checked before the Rust changes. They cover both vowels with all
13 supported consonants, all vowel pairs involving `u`/`U` and existing `a`/`i`,
neighboring-vowel transitions, digits, boundaries, mixed Unicode, and words.
All 173 cases now match the pinned parser. Existing context boundaries and
per-call reset behavior apply to both new vowels; for example, `কU` → `কঊ`,
`k1u` → `ক১উ`, and `u a` → `উ আ`.

That increment left uppercase `A`/`I`, remaining vowels, unsupported consonants,
conjuncts, and phonetic punctuation/escapes unimplemented. The next group below
adds `I`. In particular, `` u` `` remains `উ` followed
by a backtick rather than the reference's standalone U+09C1 sign. The gap probes
at that step were `I`, `kkh`, `K`, `` k`h ``, and `` u` ``.
No dependencies, composition controls, or platform integration were added.

## Third vowel group

Added on 2026-10-28: uppercase `I`, preserving the distinction from lowercase `i`.

| Context | `I` output |
| --- | --- |
| Start, or after a digit/unmatched character or supported vowel | ঈ (U+0988) |
| Immediately after a supported consonant token | ী (U+09C0) |

For example, `ki` → `কি` (U+0995 U+09BF), while `kI` → `কী` (U+0995 U+09C0).
The engine follows the typed case without spelling correction: `nIti` → `নীতি`,
`bhUmI` → `ভূমী`. An `a` immediately after `I` produces য়া (U+09DF U+09BE),
as it already does after `i`/`u`/`U`: `kIa` → `কীয়া`. Other adjacent vowels stay
independent; for example, `Iu` → `ঈউ`, and repeated `II` → `ঈঈ`.

The 52 independently authored [fixtures](../tests/fixtures/vowels-i-long.tsv)
were checked against the pinned parser before the Rust changes. They cover `I`
after all 13 supported consonants, every pair involving `I` and an existing vowel,
longer vowel transitions, digits, separators, mixed Unicode, and words. All 225
cases match the reference. Boundary and separate-call regressions now include
`I`; copied Bangla still ends consonant context (`কI` → `কঈ`).

Uppercase `A`, remaining vowels, unsupported consonants, conjuncts, phonetic
punctuation/escapes, and composition/platform integration remain incomplete.
For example, `` I` `` remains `ঈ` followed by a backtick, while the reference
produces the standalone U+09C0 sign. Current gap probes cover `e`, `kkh`, `K`,
`` k`h ``, and `` I` ``. No broader compatibility or performance claim is made.

## Compatibility and performance evidence

Before claiming Avro compatibility, validate against the pinned reference and
document expected behavior independently. Build a fixture set covering vowels,
context-dependent forms, consonants, conjuncts, case sensitivity, punctuation,
escapes, digits, and backspace sequences. Record the origin and license of any
imported fixtures or data; do not assume a public rule table is MIT licensed.

Measure conversion latency across realistic word lengths and long pasted/input
buffers. Measure adapter overhead and added memory separately from Fcitx5's own
baseline. Record hardware, build mode, workload, and measurement method before
setting release budgets. No speed or memory claims have been validated yet.

## Small development steps

Each step should produce a reviewable result and a plain-language walkthrough.
Do not implement all steps as one change.

1. **Project agreement:** requirements, developer instructions, MIT
   license, and documented unresolved choices. No application scaffolding.
2. **First conversion slice:** pin the compatibility reference, then create the
   minimal Rust library, a few independently authored examples, and focused
   tests. Explain raw input, rule matching, and Unicode output. No Fcitx5 yet.
3. **Rule coverage:** expand in small groups with regression fixtures. Track
   incomplete behavior; a few working examples do not establish full parity.
4. **Composition:** settle the interaction table, then add editable state,
   backspace, Bangla digits, literal Latin choice, and commit/cancel behavior.
5. **Fcitx5 feasibility:** build a minimal local adapter, validate interoperability
   and preedit/commit on the actual Wayland test environment, and document builds.
6. **End-to-end typing:** connect the controller, two-choice UI, and lifecycle
   handling. Test native Wayland GTK and Qt applications and a browser; record
   Electron and XWayland results separately where available.
7. **Release preparation:** address compatibility gaps, measure resource use,
   document supported versions and installation/removal, and prepare packaging
   for the first distro. Do not expand to IBus or Windows in this step.

## Decisions needed later

- Expand phonetic coverage in small groups, using the pinned parser directly
  without dictionary suggestions or autocorrection.
- Finalize candidate selection, Enter, Escape, punctuation, navigation, and
  focus/switching behavior before building composition and integration.
- Confirm the display name before public packaging.
- Record CachyOS, Plasma, Fcitx5, application versions, and CPU architecture during
  environment setup; choose minimum supported versions from actual validation.
- Revisit the Rust baseline as needed; choose an interoperability method and
  packaging format when integration establishes their requirements.

Resolve each before implementing the behavior or making the corresponding
support claim.
